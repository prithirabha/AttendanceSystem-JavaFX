# Design decisions

Why the project is built the way it is, and what would change if a requirement changed.

## H2 instead of MySQL

The app started on MySQL, which meant installing and setting up a server before the first run.
It now uses embedded **H2**: the database is a file in the user's data folder, created on first
start. Anyone who clones the repo or downloads an installer can log in a minute later. For a
single-user desktop app that is the right trade-off, because there is no shared server to keep
running.

The cost is that two computers can't share data. If the app ever needed that, a server database
would be the move. The code is set up so that switch stays small:

1. Point the app at the server with `ATTENDANCE_DB_URL` (for example
   `jdbc:mysql://host/attendance`), `ATTENDANCE_DB_USER` and `ATTENDANCE_DB_PASSWORD`.
2. Add the JDBC driver (`com.mysql:mysql-connector-j`) and Flyway's `flyway-mysql` to `pom.xml`,
   with a matching `requires` in `module-info.java`.
3. Give MySQL its own migrations, e.g. `db/migration/mysql`, because `V1__schema.sql` uses
   H2's `GENERATED BY DEFAULT AS IDENTITY` where MySQL uses `AUTO_INCREMENT`. Then make
   `DatabaseMigrations` pick the folder from the URL.

Nothing above the DAOs changes. The DAO queries already stick to SQL that both databases accept
(`CAST(... AS DATE)`, `CURRENT_DATE`, `LIMIT ?`).

## Flyway migrations

The repo used to contain a binary `.mv.db` file and an old SQL dump that didn't match it. Now the
schema is plain SQL in `src/main/resources/db/migration`. Flyway runs any file that hasn't run
yet and records it in `flyway_schema_history`. So:

- a fresh install and an upgrade from an older version follow the same path
- schema changes are reviewed in a pull request like any other code
- tests build their databases from the same files the app uses

## DAOs and services

The original dashboard controller was 1,800 lines with SQL built by string concatenation, so a
name like `' OR '1'='1` changed what the query did. The SQL now lives in four DAOs and always
uses `PreparedStatement`. The rules (required fields, duplicates, who may delete what) live in
services. Both can be unit-tested without starting the UI, and the controllers only connect
screens to services.

A full ORM such as Hibernate would be too much for four tables. Plain JDBC keeps every query
visible.

## bcrypt for passwords

The original login already checked bcrypt hashes, and that stays. The hashing now lives in one
small class, `Passwords`, and new users get hashes with cost 12 (`jbcrypt`). Why bcrypt:

- each hash has its own random salt, so equal passwords don't give equal hashes
- the cost factor makes guessing slow even if the database file is copied

A fast hash like SHA-256 would be the wrong tool here, because speed helps the attacker.

## The demo login hint

Every release ships the demo logins, and the README prints them. The login screen shows a hint
with them, but only those that still work: when it opens, it tries `admin` / `admin123` and
`employee` / `employee123` in the background (bcrypt is slow on purpose) and hides the lines that
fail. A real install whose passwords were changed shows nothing.

- The hint only ever tries those two usernames. It shows before anyone has logged in, so listing
  "other accounts that still have a weak password" would hand an attacker a list.
- An account renamed but still on a demo password is caught after login instead: the success
  message becomes a warning to change it.
- When the database has no accounts at all (a fresh install), the app opens a one-time setup
  screen that creates the first Admin (see *First-time setup* below). There is still no forced
  password change for an account that already exists: the hint and the after-login warning cover a
  demo password that lingers.

The H2 database itself also has a user and password (`admin` / `admin`). Those stay as they are:
the database file isn't encrypted, so anyone who can copy it can read it without them. Keeping the
data folder private is what protects it.

## First-time setup: the first administrator

A fresh install starts with an empty database and no accounts, so there is no one to log in as.
The app notices this at start (no users at all) and opens a one-time setup screen that asks for a
username and password and creates the first administrator. After that it hands over to the normal
login screen.

Creating a user normally needs an Admin already logged in. The first admin is the one exception,
so the method that makes it runs only while the database has no users; once any account exists, it
refuses. That keeps the Admin-only rule on every other way of adding a user.

The new account is always an Admin, whatever the form said, and its password must pass the same
strength check as any other. There is still no separate "demo or real" choice or forced password
change: the setup screen exists only so a fresh install has a safe way to make its first account
instead of shipping one that everybody knows.

## jpackage installers

`./mvnw -Pdist package` builds an app that doesn't need Java installed:

- `jlink` makes a trimmed Java runtime
- `jpackage` bundles that runtime with the app

The release workflow runs this on Linux (folder and `.deb`), Windows (zipped folder) and macOS
(`.dmg`) when a `v*` tag is pushed. Windows gets a zip instead of an `.msi` because an MSI needs the
WiX Toolset.

`jlink` only accepts real Java modules, and H2, Flyway and jbcrypt aren't. So the runtime holds only
JDK modules, and the libraries sit beside it on the module path.

## Staying on the latest stack

- **Java 25**, the current LTS. The Maven Enforcer plugin stops the build with a clear message on
  an older JDK. The Maven wrapper (`./mvnw`) downloads the right Maven, so only a JDK is needed.
- **Dependabot** opens a pull request each week for new library, plugin and GitHub Actions
  versions. CI tests each one on Linux, Windows and macOS before it can be merged.
- A **Java 27 CI job** runs the build on the next JDK. It is allowed to fail, and works as an
  early warning before the next upgrade.

## Card readers

- **Keyboard mode.** Almost all USB RFID readers, and barcode or QR scanners too, act as a
  keyboard: they type the card's ID and press Enter. So the Attendance screen has one text field
  that reacts to Enter. That supports every such device with no drivers and no library, and it
  can be tested by typing. Every scan goes through `AttendanceService.scan(cardId)`: an open entry
  today means check out, otherwise check in.
- **A photo, not a live camera.** The phone stands in for a reader through a small page the app
  serves on the Wi-Fi. Browsers allow a live camera only on https pages, and https on a LAN
  address needs a certificate the phone trusts. A photo upload
  (`<input type="file" accept="image/*" capture>`) works over plain http, and the app decodes the
  QR code from the photo with ZXing. The page shrinks the photo before sending it, since a phone
  camera's several megabytes would be slow on a busy Wi-Fi and the app never reads more than
  1600 pixels anyway.
- **Reading tilted photos.** Card IDs are short, so cards get the smallest QR code (version 1).
  It has only the three big corner squares and no smaller mark for the fourth corner, so ZXing
  guesses that corner as if the card lay flat, and a photo taken at an angle fails.
  `QrPhotoReader` then tries fourth corners around that guess, nearest first, and the code's
  error correction turns down every wrong one. It also reads each photo at 1600 and 1000 pixels,
  because corner squares one size misses, the other often finds. BoofCV, a library that solves
  this, was tried first: its jars split packages between modules, which a Java module app can't
  load.
- **Other readers.** A serial or Arduino reader, or a reader with its own SDK, would be one more
  class that reads IDs and calls `AttendanceService.scan` on the UI thread, the same way
  `PhoneScanServer` does. Nothing else changes.
- **Security of the phone server.** It is plain http on the local network, so:
  - it runs only while "Use phone as scanner" is ticked, and stops on untick, logout and exit
  - every URL must start with a random 128-bit token (`SecureRandom`); anything else gets 404.
    Switching it off and on makes a new token
  - photos over 15 MB are refused, and so are photos whose header claims over 64 megapixels.
    The size is read from the header before decoding, as a small file can claim a picture that
    would take gigabytes of memory
  - the text read from a QR code comes from outside like a typed ID, so both get the same
    checks: at most 64 characters and no control characters
  - a photo with several QR codes is refused, as picking one could check in the wrong student
  - an image reader or QR reader that crashes on a crafted file gives a plain answer (415 or
    422), never a server error; the QR reader's crash is logged
  - requests run on a small pool of threads, and a connection that stalls or sends an over-long
    body is dropped after a timeout, so one bad connection can't block the scanner for everyone
  - it listens on port 8765, so a firewall rule can allow just that port. If another program has
    8765 it takes any free port, and the screen says that 8765 was busy and which port to allow
  - it can only check students in and out, never read or change other data

  Anyone on the same network who sees the pairing QR code could scan cards, so it is meant for a
  trusted Wi-Fi.

## Backups: a separate password and chunked AES-GCM

A backup holds every student's data, so it is locked with a password. It is its own backup
password, not an admin login:

- the app keeps logins only as one-way bcrypt hashes, so it has nothing to lock a file with
- a backup should still open after a login password changes or that admin is deleted
- it needs at least 12 characters, more than a login, because a stolen file can be guessed at
  offline, with no login screen to slow the guessing down

The format uses only what is built into Java, so it adds no dependency:

- PBKDF2-HMAC-SHA256 with 600,000 rounds (the OWASP advice) turns the password into an AES-256
  key, which makes each guess slow
- the body is AES-GCM in 1 MiB chunks, so a backup with many photos never has to fit in memory
- each chunk's nonce holds its number and a "last" flag, and the header is checked with every
  chunk, so a changed, reordered or cut-off file fails like a wrong password does

Not done, on purpose: a cloud upload (it would need accounts, a stored key and student data
sent to an outside company; saving into a synced folder does the same) and automatic backups
(only if people forget to use the button).

## Restoring a backup only trusts its data, not code

A backup to restore is a file from outside the computer, so the restore treats it as untrusted.
An H2 database can store runnable code: an *alias* (a small Java function) or a *trigger*. If the
app simply opened a database that held such code, the code would run the next time the app wrote
a row — enough for a crafted backup file to take over the computer.

So before a restored database is ever swapped in, the restore opens it **read-only** (which never
runs that code) and refuses it if it holds any user-defined routine or trigger. The app's own
schema has none — only plain tables and auto-numbered ids — so a real backup always passes, and a
crafted one is caught. Listing the routines and triggers does not run them; only an insert or a
query would, and the restore does neither.

A detail worth recording, because it surprised us: whether a trigger can run at all depends on how
the app is started. In the released app, which runs as a Java module, H2 can neither compile an
inline-Java trigger nor build a trigger from one of the app's own classes (the module system
blocks it), so triggers only bite when the app runs on a plain classpath, as it does in
development. An alias, whose code can stand on its own, runs either way. The check refuses both, so
it holds whichever way the app is launched.

Known limit: this refuses stored code, not an H2 "linked table" (which reaches out to another
database when it is queried). Rebuilding the data into a fresh database would avoid even that, but
costs far more code; refusing routines and triggers closes the way a backup could run code, which
is the real risk.

## Known gap: database work on the UI thread

Every database call runs on the JavaFX application thread, the same thread that draws the
window. With a local H2 file and a few hundred rows this takes milliseconds, so nobody notices.
With a remote database or large tables, the window would freeze during each call.

The next step would be to run each service call in a `javafx.concurrent.Task` on a background
thread. The table would be filled in `setOnSucceeded`, which runs back on the UI thread, and an
alert shown in `setOnFailed`. The services don't touch the UI, so they would not need to change.

A second small gap: if the database can't be set up at start, JavaFX prints the error and exits.
A dialog would be friendlier.

## UI design

![Login before and after](screenshots/before-after-login.png)
![Dashboard before and after](screenshots/before-after-home.png)

The old look mixed gradients and colors chosen screen by screen. The refresh changed only CSS and
small FXML spacing, so the UI tests passed unchanged.

- **Design tokens.** Every color is defined once in `theme.css` (`-color-primary`,
  `-color-surface`, `-color-text`, ...). The other stylesheets use only these names. A new
  look, or a dark mode, means editing one file.
- **Contrast.** Text colors meet WCAG AA, at least 4.5:1 against their background. For
  example, muted text `#475569` on white is about 7.6:1.
- **One font.** Inter (SIL Open Font License) ships in the app and is loaded at start, so the
  look is the same on every OS. It uses a fixed size scale: 12 / 13 / 15 / 18 / 24 px.
- **Roles, not one-offs.** Buttons come in primary, secondary and danger styles. Keyboard focus
  gets a visible ring (`:focus-visible`) that mouse clicks don't trigger. The sidebar marks the
  open screen with a style class instead of inline styles set from Java.
- **MaterialFX's own stylesheet is not loaded.** Loading it for the whole app would restyle every
  screen. So `login-style.css` styles just the two MaterialFX fields on the login screen. One
  example: their inner text box is made transparent, or it would hide the floating label.
